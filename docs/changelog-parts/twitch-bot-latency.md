## Twitch bot: it reacts faster / Bot Twitch : il réagit plus vite

*EN: the bot answers chat commands without waiting for other modules or for Twitch, validates home rewards by itself, and sends a repeating message at its time. For Curiosa 0.6.4 or later. Module touched: Twitch bot 1.11.0.*
*FR : le bot répond aux commandes du chat sans attendre les autres modules ni Twitch, valide tout seul les récompenses de la maison, et envoie un message répété à son heure. Pour Curiosa 0.6.4 ou plus. Module touché : Bot Twitch 1.11.0.*

### What changes for you / Ce qui change pour vous

- **EN: Chat commands answer faster.** The bot used to read the calendar, your partners, your networks and the follower count before answering any command, and asked Twitch whether you were live every time. It now reads only what the command needs, answers from the last reading (less than a minute old) for the "only when live" check while it refreshes in the background, and writes its journal after the reply. A command in a quiet chat no longer waits for a slow calendar or a slow Twitch.
- **FR : les commandes du chat répondent plus vite.** Le bot lisait le calendrier, vos partenaires, vos réseaux et le nombre de followers avant de répondre à n'importe quelle commande, et demandait à Twitch si vous étiez en direct à chaque fois. Il ne lit plus que ce dont la commande a besoin, s'appuie sur la dernière lecture (de moins d'une minute) pour le contrôle « seulement en direct » pendant qu'il la renouvelle en arrière-plan, et écrit son journal après la réponse. Une commande dans un chat calme n'attend plus un calendrier lent ni un Twitch lent.
- **EN: Home rewards are validated by themselves.** Once your home has played the action, the reward is marked as done within seconds, instead of waiting for the next chat message or reward (which could take minutes in a quiet chat).
- **FR : les récompenses de la maison se valident toutes seules.** Dès que la maison a joué l'action, la récompense est marquée comme faite en quelques secondes, au lieu d'attendre le prochain message du chat ou la prochaine récompense (parfois des minutes dans un chat calme).
- **EN: A repeating message goes out at its time.** A message that asks for a few chat lines is now sent within a minute of its time if the lines are already there, instead of at the next chat line. A silent chat still gets nothing, and a message that asks for no line still waits for a chat line, as before.
- **FR : un message répété part à son heure.** Un message qui exige quelques lignes de chat part maintenant dans la minute qui suit son heure si les lignes sont déjà là, au lieu d'attendre la ligne de chat suivante. Un chat resté muet n'envoie toujours rien, et un message qui n'exige aucune ligne attend toujours une ligne de chat, comme avant.

### For developers

- **Twitch bot 1.11.0** (`dataVersion` 6 and `minCore` 0.6.4 unchanged; `twitch-connector` untouched). Measured over a fake Twitch with a modelled cost per call (database 2 ms, service call 3 ms, topic read 4 ms, Helix 60 ms), reply after receipt: quiet chat 184 → 81 ms, quiet chat with a calendar module answering in 1.2 s 1365 → 76 ms, quiet chat with Twitch answering in 400 ms 855 → 412 ms, warm 92 → 72 ms, cold restart 407 → 387 ms (one Helix GET /streams is unavoidable). Bench: `tests/twitch-bot-latency.bench.mjs`; regression tests: `tests/twitch-bot-latency.test.mjs`; helper `tests/helpers/latencyWorld.mjs` (the real bot and the real connector over `fakeTwitch`, with spans per call).
- Replies now leave through a FIFO queue (3 at a time) in `listen.mjs`: faster processing would otherwise let 17 or more simultaneous replies hit the core network client's 16-per-host admission limit and be lost. Causes fixed: the chat path awaited `reconcile` (rewards, up to 3 s of `ha.state`) and a state write before `processChat`; `gather` read all four sources for any command and any `!word`; the freshness window of 15 s meant a quiet chat always paid every cross-module read; the "only when live" gate always waited for a Helix GET /streams; the configuration and the account check were read for every message; the journal was awaited before the call ended and so delayed the timers pass.
- `sources.mjs`: stale-while-revalidate for planning, partners, networks and followers (`timing.staleMs`, 10 min), one in-flight read per key, `liveGate` (≤ 60 s old, refreshed in the background) for the "only when live" check while `liveState` stays fresh for `{jeu}`; `gather(ctx, channel, need)` reads only what is asked; `warm`. `commands.mjs`: `loadConfig` is remembered per instance and dropped by `mutate`, `migrateConfig` and `forgetConfig`. `listen.mjs`: `diagnoseFast` keeps a *ready* diagnosis 5 s, shared by concurrent calls, dropped by a failed send, `declareScopes` or a changed account setting. `engine.mjs`: `needsOf(cmd)`, reads in parallel, `deferLog` (the webhook awaits `result.logged` before returning: nothing is lost). `webhook.mjs`: reconcile, draw feeding and the "last message" note run beside the reply. `redeem.mjs`: `followUp` (five re-reads at 1.5, 4, 9, 20, 45 s while a home reward waits), `reconcile({ house: false })` for the redemption path. `timers.mjs`: `processTimers(ctx, null, { tick: true })` and a per-instance run queue. New task `tick` (every minute): warms the sources, runs the timers pass, reconciles rewards when they are on.
- Not changed on purpose: the 12 replies per 30 s default and the 18 maximum (Twitch allows 20 for a normal account and 100 for the broadcaster and moderators; a command over the budget is refused with the reason "rate", never queued), the transport (EventSub webhook), and the rule that a repeating message that needs no chat line waits for a chat line.
